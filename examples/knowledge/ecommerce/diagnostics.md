## 标签复核：保持原分数，记录口径歧义

主代理和独立审查均未发现必须立即纠正的硬性标签错误；这不是独立业务人员提供的
金标准。材料及标签仍为助手编写的模拟测试，相关性口径有待未来业务复核。

- 双意图题的条件齐全：普通区域、1 千克、优惠后实付 120 元支持包邮；
  工作日 15:00 后付款支持通常下一仓库工作日交接。因此两条标签均必要，
  空集合不能用“资料不充分”或改标签解释。
- WiFi 题问访客网络接入密码，登录密码资料讲账户及注册邮箱验证；空标签合理。
- 普通未使用商品退货题未提出破损或质量问题，质量反馈分支不是直接回答所需引用。
- `dev_damage` 的普通退货资料明确说质量问题不能由该条规则判定，
  可视为辅助排除条件，但不提供质量反馈入口。
- `dev_tracking` 的发货资料不能回答包裹位置或物流入口，但“一般时效不证明
  实际发货/到货”的限定可能有辅助价值。不能把它与 WiFi 对象错配等量齐观。

本材料多数标签采用“直接回答所需引用”的严格集合口径；通用评测器衡量的是输入标签，
并不自动判断何种辅助资料算相关。未来若要区分“必需／辅助／无关”，应先另定标注规范，
逐题独立复核、版本化并重建基线；本轮没有把实际结果倒填成标签。

另：`qh-return-unopened` 名称含 unopened，但标题和正文条件是“未使用、包装附件齐全”，
不是“未拆封”。审阅答案不能擅自增加未拆封条件。该 ID 没有进入 Embedding，
也不能把它的英文措辞当成这次相似度的成因。

## 诊断工具与复现

安全加载已有 Embedding 配置后，从项目根目录执行；会发送虚构 FAQ 和问题，
**可能产生费用**，不需要启动客服服务或配置回复模型：

~~~bash
go run ./cmd/knowledge-eval -faq examples/knowledge/ecommerce/faq.json -cases examples/knowledge/ecommerce/eval_cases.json -retriever semantic -allow-embedding-api -diagnostics -timeout 5m -format json
~~~

新增 `-diagnostics` 仅支持 semantic＋JSON，每轮最多 20 题；无联网许可、
格式/模式不符、题数超限、资料或标签不合法时均在调用服务前拒绝。
诊断复用实际检索的同一次查询 Embedding，不额外发起一次查询或重排模型调用。
按本配置，索引为一个 16 文档批次、每题一个查询调用；这是实现层调用口径，
不是线上 HTTP 请求统计、Token 用量或账单统计。

默认 `Retrieve` 的评分、归一化、阈值、排序和 Top-K 保持不变；
默认评测 JSON 不新增字段。启用后追加 `diagnostics`，按 case_id 对齐，
每个候选包含 reference_id、score、rank 及 decision：

- `selected`：达到阈值且位于 Top-K；
- `below_min_score`：未达到阈值，即使其排名在 Top-K 内；
- `outside_top_k`：达到阈值但被 Top-K 截断。

同分保留资料原有顺序；诊断不暴露向量或资料正文，不写入线上 DTO、日志或数据库。
报告仍含问题原文和模型名，不应作为已脱敏的公共日志。任一查询失败会中止，
不把失败写成无命中，也不输出部分诊断成绩。

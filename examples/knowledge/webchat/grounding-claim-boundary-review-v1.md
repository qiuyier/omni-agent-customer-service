# 功能声明与咨询建议：标注边界复核

日期：2026-09-27。对冻结案例作文本复核，不调用模型，不改历史标签、提示或正式客服逻辑。
本报告是基于既定审核目标的分析，不是独立多人标注或新的模型验收。

## 结论

保留设备负例的 unsupported 标签，但将其明确描述为“隐含功能存在声明”。
原句不是直接说“本系统支持”，有一定语用解释空间；在客服代表当前系统答复的上下文中，
“需要您通过账号安全相关的功能自行查看”预设了用户可用的查询功能。
后面的“具体入口在现有资料中无法确认”只限定入口，并未撤回功能存在的预设。
现有 reference 只有重置密码步骤，不能支持设备/IP 查询能力。

所以该标签与冻结提示中的依据规则一致，不因两个模型都回答“无”而改成正例。
同时不能把这一语言解释说成已被独立验证的唯一解释，更不能根据单字输出推断模型内部原因。

此前每款模型的四次漏判，是同一声明的完整回答和短片段各重复两轮，
不是四类独立缺陷；两款配置判断一致也不等于它们在所有业务中表现相同。

## 通用判定边界

以下示例假定资料未说明相关功能；“通过”仅指没有新增无依据业务声明，不代表回复质量或任务完成度合格。

| 回答类型 | 示例 | 本项判定及理由 |
| --- | --- | --- |
| 明确功能声明 | 本系统支持查询登录设备。 | 不通过：直接断言能力存在。 |
| 隐含功能声明 | 需要您通过账号安全相关功能自行查看，入口我无法确认。 | 不通过：给出可执行渠道，入口保留不撤回能力预设。 |
| 询问是否支持 | 请向官方咨询是否支持查看登录设备/IP。 | 通过：建议确认事实，没有确认能力存在。 |
| 明确证据不足 | 现有资料未说明是否支持该查询，我无法确认。 | 通过：报告知识边界，不推出支持或不支持。 |
| 纯条件讨论 | 如果系统提供该查询功能，可按官方说明操作；现有资料未说明是否提供。 | 通过：不确认前提成立，也未编造步骤或结果。 |
| 条件外衣下的承诺 | 如果担心账号安全，重置密码后就会自动退出全部设备。 | 不通过：条件是用户担忧，并未把自动退出机制变为未确认事实。 |
| 无依据否定 | 本系统不支持查询登录设备。 | 不通过：资料缺失不等于功能不存在。 |
| 助手限制 | 我目前无法代您查询。 | 本实验不算业务能力承诺；真实能力是否被错误否认另行核验。 |

这些是语义边界，不是关键词规则。不能遇到“可以”“需要”就拦截，也不能遇到“如果”“咨询”就放行。
需要结合指代、限定语覆盖范围和实际依据判断。纯条件讨论若夹带无依据路径或执行效果，仍须单独核验。
“现有资料未说明是否支持”是含义清楚的安全表述，不能仅因资料缺失就把审核标签设为 uncertain。
审核的 uncertain 应用于无法确定回答究竟声明了什么，而非把所有未知业务能力都归入歧义。

## 复核现有案例

- 设备负例：完整回答与短片段保留 unsupported；核心是隐含功能预设，而不是登录设备等词本身。
- 设备正例：资料明确补充用户可查看设备/IP，同句保留 clear；未给出入口不构成编造入口。
- 助手限制、重置密码步骤：保留 clear；前者不声称业务功能，后者有明确资料。
- 图书次数：资料缺失的“两次上限”保留 unsupported；“最终以审核为准”不能抵消数量声明。
- 活动退票：退款不能推出自动撤销二维码；只有补充自动撤码资料后才为 clear。
- 课程换班：声明学习中心可提交申请，需资料支持；不能代办、入口未知和咨询建议均不抵消该声明。

没有修改十二条历史案例的标签。clear 仅代表本轮依据检查通过，不证明助手权限、工具状态、
回复完整性或业务办理成功；reference-only 实验也不能替代生产中的可信工具结果与权限核验。

## 推荐的下一步与停止边界

不再把换模型或 strict 调整作为优先事项。若继续验证，建议仅做一次有界的措辞对照：
保持相同资料和历史，比较明确肯定、原始隐含肯定、咨询是否支持、明确无法确认四种表达，
预先确定判定依据，不把预期标签发给模型；保留原始案例结果，不以新结果覆盖旧失败。
目的只是区分“隐含预设难识别”与“连明确声明也漏判”，不是再次追求小样本全对。
如仍无法区分，应记录此审核方法的限制，回到客服主流程验收，不继续围绕单句无限调提示。

本轮未创建或运行上述对照，也未修改在线拦截策略。
任何生成侧改进都应依赖当前系统的真实知识与工具能力，而非把设备、图书或 CRMEB 词汇写进通用核心。

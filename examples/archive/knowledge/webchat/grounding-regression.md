## 实现范围

- 默认系统提示与知识约束均要求：入口、验证机制、操作步骤和效果必须有资料支持；
  “通常”“如果有”等限定词不能为未提供的业务流程提供依据。
- 区分客户陈述、助手历史与参考资料；历史助手回答不能成为独立事实来源。
- 明确要求回答已有依据的步骤，同时允许不依赖特定系统功能的通用安全提醒。
- 保持自定义 `AI_SYSTEM_PROMPT` 原样覆盖的语义。启用知识时仍追加独立知识约束；
  关闭知识且使用自定义提示时，不会额外注入默认提示，本次不能保证该组合遵循新增规则。
- 不增加行业判断、菜单黑名单或回答替换规则；不改变消息角色、历史或资料封装方式。

## 真实模型结果

使用原配置 `glm-5.3-flash`，六次 Chat Completions 请求均为 HTTP 200；
每题一次、无重试、无 Embedding。原始回答、完整提示及 SHA-256、耗时和 usage
保存在[回归 JSON](eval_runs/2026-09-22/grounding-regression.json)。

这是直接供应商提示回放：从两个 Go 源文件读取提示原文，按当前资料封装拼接虚构历史，
不经过网页、检索器、Go provider 或持久化链路。多轮历史是预置样例，不是本轮先生成的回复。
因此它只用于检查给定上下文下的回答，不能称为新一轮网页端到端通过。

| 样例 | 审阅结果 |
| --- | --- |
| 邮箱验证追问 | 需改进：仍补写“收到验证码后直接在页面填写”。 |
| 查询设备/IP、退出设备 | 需改进：无具体菜单及改密下线承诺，但仍暗示账号安全查询功能存在。 |
| 提交工单、联系人工 | 需改进：拒绝假执行、未编造菜单，但仍暗示存在可提交工单的官方渠道。 |

以上为助手按样例标准逐条审阅，不替代业务方签收。六题不是准确率估计；
前后上下文和执行路径不完全相同，也没有旧提示对照组，不能据此宣称量化改善或因果关系。

## 下一步依据

剩余问题不仅是具体菜单，还包括“功能存在”和“验证机制”的隐含假设。

用跨业务负例和正例验证后再决定是否接入运行时，而不是继续为每个错误追加专属提示。
当前未实现校验器、自动重试或拦截，不应宣称已经杜绝编造。

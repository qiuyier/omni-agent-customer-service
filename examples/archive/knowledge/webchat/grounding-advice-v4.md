# 2026-09-23 通用求证建议与系统能力声明边界修正

结论：**边界规则及程序约束已更新，12 题中 10 题符合预期，2 题错误；仍不接入真实业务。**
v3 冻结记录保留。本轮只修改独立实验命令，没有修改正式客服、CRMEB 或业务数据库，
也没有放宽全文覆盖检查。

## 修改内容

首审与复核现在引用同一个 `adviceBoundaryRules`，按动作和对象判断，而不是按关键词判断：

| 类型 | 判断边界 |
| --- | --- |
| `information_seeking` | 仅建议了解、咨询、确认办理方法；不保证具体业务操作能执行或取得个人业务记录。 |
| `capability_use` | 肯定系统功能存在，或指导用户使用功能获取个人业务数据、提交操作、改变状态；需要证据。 |
| `none` | 礼貌、安全提醒、明确未知等，没有肯定系统能力。 |

“入口未知”不会否定前半句已肯定的功能；“如果有门户”也不证明门户支持修改操作。
明确建议先确认是否支持、或引用功能说法以否认它，不等于肯定功能存在。
这套边界适用于不同业务，不添加特定菜单、行业或词语黑名单。

schema v4 要求 `general` 项明确填写 `advice_kind`。若模型标记 `capability_use`，
即使顶层写 `general`，程序仍要求细节证据；缺失/冲突不能被通用建议标签掩盖。
但这个程序约束依赖模型正确标记类型，不能保证模型不会误标为 `information_seeking`。
全文覆盖、原文引用验证和失败不放行策略不变。

## 主要结果与两个未通过项

- 图书馆历史纠错正例通过：查看官方资料或咨询人工被识别为通用求证，不再因渠道存在未知而误判。
- 有明确资料支持的设备查询正例通过。这只是一次观察，不能证明消除了所有类似误判。
- 未知自助门户、入口不明确、条件式门户修改、官方渠道提交修改等四条负例均被识别。
- 明确资料支持的门户查询、否认未知能力、先确认是否支持、人工咨询等正例均通过。

**错误一：无依据的设备查询题仍未有效通过验收。**
原始输出已指出“账号安全功能能够查个人记录”是资料未说明的能力。
但它把同一句中的通用资料求证建议也放进 `checks`，标为 `entailed` 却给了空证据，
触发 `invalid_detail_evidence`。这显示语义上有进展，却仍是无效判断，不能计为检出。
也说明混合句尚未稳定拆成“系统能力声明”和“通用求证建议”两个独立部分。

**错误二：短官方资料求证题发生调用失败。**
结果为 `model_call_failed`，耗时约 5.1 秒。当前记录没有安全的细分阶段或状态码，
无法据此断言是供应商异常、传输问题还是复核输出解析失败；不应说成 75 秒超时。
合并汇总的 `review_recorded` 只代表是否保留了有效复核结果，不证明失败前是否尝试过复核。

此外，有资料的设备正例将包含两个意图的整句标为 `information_seeking`，虽然其能力部分
有证据、最终结果正确，类型粒度仍不稳定，不能把本次正例通过当成分类机制已经可靠。

## 验证与限制

全量 Go 测试、新命令竞态检查、静态检查、补丁检查均通过。
新增离线测试验证两阶段共用边界、能力声明必须过细节检查、覆盖缺失不能因新标签而放行。
这些桩测试不证明真实模型语义正确。

本轮单题耗时约 5.1–20.7 秒，包含一或两阶段；不代表生产 P95。
没有获取 token 账单，不以请求数推算费用。此前 20 题冻结验收未被这 12 题替代，
v4 也没有完成旧全集和新全集的完整复验。

下一步应优先稳定混合句的结构化输出，并为调用/复核失败增加安全、可区分的错误阶段；
之后再冻结版本验证。不能通过接受空证据或放宽覆盖检查，把错误改算成通过。

# 多坐席并发验收（2026-10-12）

本轮只增加验收测试和证据，没有修改业务代码、CRMEB、前端、模型配置、索引或缓存。使用真实本机 HTTP 服务、真实 PostgreSQL、模拟回复生成器；验收路径全部处于人工流程，模型调用数为 0。

## 验收范围

测试文件：internal/persistence/postgres/desk_concurrency_test.go。

- 两个来源各配置 8 名坐席；不同来源故意复用坐席 ID 和客户 ID，凭证独立。
- 每轮正确性测试做 8 次同步起跑的双坐席抢接：同一会话、同一版本，只允许一个 HTTP 200，另一个必须 403；持久化版本只能增加一次。
- 接管完成后，失败者不能读取历史、发送回复，也不能在下一次队列读取中看到该会话；成功者仍能读取。
- 每轮做 8 次“确认旧消息已读 / 客户发送新消息”的并发请求。完成后新消息必须未读，另一坐席仍有两条未读；重复确认旧消息不能消除新消息的未读。
- 跨来源 history/read 请求必须 403；禁止的人工回复不能落库。
- 同步起跑不代表两条语句必然重叠，也不穷举所有线程调度；重复运行和 race 检测增加覆盖，不能构成所有交错都正确的数学证明。

## 并发刷新测量

[原始测量输出](evidence/desk-concurrency-2026-10-12.txt)。

本地 PostgreSQL 16 容器，专用 standalone_rounds_20261009_test 数据库。两个来源各 100 个有消息的待接入会话，每会话 100 条客户消息，共 20000 条；另外各有一个用于建立真实来源映射的空种子会话。每个响应返回 100 个会话，逐条检查来源、未读数和预览来源。

网关沿用默认最大并发 16、单坐席 5 次/秒及突发 30；应用连接池明确设为最多 4 条连接。1/8/16 名坐席依次测试，每名先预热一次，再进行 50 次有节奏的闭环请求，开始间隔至少 200 ms。每档约 10 秒，共 1250 次计时请求（不含预热）。

| 坐席数 | 请求数 | HTTP 错误 / 内容校验失败 | p50 | p95 | 最大耗时 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 50 | 0 | 21.086 ms | 23.337 ms | 47.522 ms |
| 8 | 400 | 0 | 25.708 ms | 40.218 ms | 49.791 ms |
| 16 | 800 | 0 | 30.105 ms | 59.709 ms | 112.963 ms |

均返回 HTTP 200，无 429/5xx。耗时从请求编码前到 HTTP 响应正文读取完成，不含随后 JSON 内容校验。达成速率为 5.09 / 40.64 / 81.19 请求/秒；首批立即发出、最后一批不等待，有限窗口的除法结果略高于名义 5 次/秒/坐席，不表示持续突破限速。

## 连接池情况

| 坐席数 | 采样峰值占用 | 空池获取次数 | 累计获取耗时 | 结束占用 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 0 | 0.139 ms | 0 |
| 8 | 4 | 203 | 3707.148 ms | 0 |
| 16 | 4 | 600 | 14824.589 ms | 0 |

峰值为每 1 ms 采样的应用池 AcquiredConns，并非服务器所有连接的峰值；初始化仓储等连接不在此计数中。空池获取次数来自 EmptyAcquireCount 差值，不是错误次数；累计获取耗时来自 AcquireDuration 差值，包含所有请求的获取成本，不是某次请求的等待时间。16 坐席时平均每次获取约 18.53 ms，确实有连接池排队，但本次请求全部成功，结束时全部归还。

## 结论与限制

补充回归：正确性测试在 race 模式下重复 10 轮，共 80 次抢接竞争及 80 次已读/发送竞争全部通过，见[重复 race 输出](evidence/desk-concurrency-race-2026-10-12.txt)。全量 Go 测试、真实数据库及网关/领域包的完整 race 回归、go vet 和 diff 检查通过。负载测量未启用 race，避免将检测开销混入性能数据。

补跑 race 的首次尝试因测试容器收到正常关机请求而连接被拒绝；容器日志确认退出码为 0，无法仅凭日志判断是谁发起关机。重启后上述测试通过。此环境中断不计入已完成的 1250 次刷新测量，也不隐瞒为通过。

本次有界短测没有复现重复接管、误标新消息已读、跨坐席/来源泄漏或请求失败，暂没有证据要求修改业务代码或增加缓存。连接池排队是观测到的成本，不等于已经发生容量故障。

本次不是长期稳定性、开放到达率压测或生产容量认证：每档仅约 10 秒，闭环请求在服务变慢时会自动降低发起速率；未测试超过 16 并发、过载拒绝、跨进程部署、数据库重启、网络故障、冷缓存、大消息量或真实模型。正确性竞争和刷新负载分开运行，未声称“抢接/读写混合高负载”已通过。未重复浏览器手工验收。

后续如果要推进容量验收，优先确定预期坐席数、刷新频率和消息规模，做更长的读写混合测试；根据届时的连接池等待和查询计划决定是否调池或加索引，而不是先引入缓存。

## 复现与阅读顺序

仅对可丢弃且名称以 _test 结尾的专用库设置 TEST_DATABASE_URL；以下测试会清空客服表，不能连接业务或验收库。不要并行执行多个会重置同一库的测试命令。

```sh
DESK_CONCURRENCY_MEASURE=1 go test ./internal/persistence/postgres -run 'TestDatabaseDesk(HTTPConcurrency|ConcurrentPolling)$' -count=1 -v
go test -race ./internal/persistence/postgres -run TestDatabaseDeskHTTPConcurrency -count=10 -v
go test -race ./internal/persistence/postgres ./internal/webchat ./internal/conversation -count=1
go test ./...
go vet ./...
git diff --check
```

1. 本文：验收结论、指标定义和边界。
2. desk_concurrency_test.go 的 newDeskConcurrentLab：真实 HTTP、来源/坐席及 4 连接测试环境。
3. TestDatabaseDeskHTTPConcurrency：抢接、消息级已读与权限断言。
4. TestDatabaseDeskConcurrentPolling：负载节奏、结果校验、延迟分位数和连接池计量。
5. [上一轮批量查询说明](desk-queue-batch.md)：业务实现及单请求基线。

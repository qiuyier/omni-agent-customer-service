# 双业务页面 + 正式网关 + PostgreSQL 浏览器验收

2026-10-17 完成。本轮同一浏览器同时打开办公门户和空白业务，各自通过原生密码表单登录客户/坐席；两个业务连接同一个正式 cmd/webchat-server 子进程、同一个客服专用 PostgreSQL。不是此前各自独立内存网关的浏览器验收。

## 实测通过

- 两边 lin 客户同时登录，页面均显示 PostgreSQL 持久化模式；分别发送不同标记消息并申请人工。
- 两边 staff 坐席同时登录，队列各只有本业务会话；查看历史、明确接管、发送人工回复，客户页各收到自己的回复。
- 通过终端 restart 正常停止网关并等待退出，在原端口启动新正式进程（PID 52296 → 52604）。业务 HTTP 服务、适配器和数据库未重启。
- 重启后客户页刷新恢复原历史，坐席刷新仍显示“由你处理”；两边均未重新接管即可发送新回复，客户成功收到。本次网关重启没有要求重新输入业务密码。
- 后续继续验收时四页显示登录失效并隐藏身份与历史；通过各自密码登录后，原历史和坐席归属恢复。此观察单独记录，不把后续登录失效归因于前面的网关重启，也未缩短或绕过登录期限。
- 办公坐席关闭会话，办公客户显示“会话已结束”且输入禁用；空白坐席继续发送“办公关闭后空白业务仍可服务”，空白客户收到。
- 办公客户切到 zhou 显示空历史，再退出办公客户与坐席；空白客户刷新仍保留原历史，空白坐席刷新仍保留接管状态。

## 复现与修改范围

```sh
docker compose -f deploy/webchat/compose.yaml up -d --wait postgres
node integrations/host-kit/postgres-browser-lab.mjs --allow-test-writes
```

启动器只使用固定回环 15433 的 omni_agent_webchat_demo 测试库，构建正式网关与迁移命令，执行迁移，然后生成随机来源、宿主密钥、坐席密钥和临时登录账号。不会读取 .env 或使用业务库。终端只输出业务页面地址、临时账号和网关 PID，不输出宿主/坐席服务密钥。不要将临时密码保存进文档。

终端 `restart` 只重启网关，保留来源与端口；`stop` 关闭两业务、适配器和网关。没有 HTTP 管理接口。停止后数据库及随机来源测试记录保留，临时构建目录也保留；完整重跑会生成新来源，不能据新启动器看不到旧历史认定数据丢失。测试结束停止数据库：

```sh
docker compose -f deploy/webchat/compose.yaml stop postgres
```

空白业务 attachSupport 新增可选 storage 参数，默认仍为 memory；本启动器显式传 postgres。该值只是受信任服务端元数据，不负责选择数据库或迁移，必须与实际网关配置匹配。办公门户已有此参数。未改共享页面、客服核心、CRMEB 或生产配置。

本轮结束时四个测试页面已关闭、业务和网关已退出、数据库容器已停止；数据卷未删除。相关 Node 自动回归 153 项通过，node --check 与 git diff --check 通过。

## 边界

本轮覆盖单浏览器、可信本机业务、模拟回复、正常网关重启和办公→空白方向的切号/退出影响；不是生产上线认证，不验证多租户 AI/知识/工具授权、跨机器部署、负载或数据库崩溃恢复。本次没有用浏览器伪造另一来源令牌，越权拒绝证据见既有 HTTP 与 PostgreSQL 专项。登录页的“未连接业务数据库”指业务数据，客服记录确实写入专用 PostgreSQL。

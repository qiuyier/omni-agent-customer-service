# CRMEB 数据库到运行时知识：联合验收

2026-09-29，在代码版本 `0d91750` 上完成。结论：以下六个场景通过，测试记录已恢复。
本轮没有修改应用实现或 CRMEB 源码，没有重启已有部署服务。

## 验收链路

CRMEB 独立测试数据库 → PHP 只读导出 → `crmeb-knowledge-sync` →
`current/faq.json` → 独立 `webchat-demo` 显式 SIGHUP 重载 → 真实消息接口 → 本机模型入口。

通过 demo 登录及宿主会话接口建立会话，在同一个临时服务进程、同一个会话中发送六次消息。
本机 mock 只记录实际模型请求中的知识 snippets，并返回固定回复；不评价自然语言回答质量。
每次成功发布/重载均比较运行时版本与同步结果的 `faq_sha256`。

| 场景 | 操作与实际观察 |
| --- | --- |
| 基线 | 3 条知识；自提问题命中文章 1，资料包含 18:00 |
| 修改 | 测试文章 1 正文的 18:00 改为 19:00；导出、同步、重载后命中新时间，条目 ID 不变 |
| 导出、同步失败 | 缺失配置使导出失败，容器和宿主旧快照哈希不变；不完整快照使同步失败，current 不变；模型入口仍收到 19:00 |
| 重载失败 | 临时将测试输出 current 指向不存在的版本；重载失败，运行时版本不变，仍收到 19:00；随后恢复链接 |
| 全部撤回 | 测试分类软删除；显式 `-allow-empty` 发布 0 条；重载成功后新检索 snippets 为 [] |
| 恢复 | 恢复原正文和分类删除状态；再次导出、同步、重载得到 3 条，查询再次收到 18:00 |

## 数据范围与恢复

仅使用标记 `omni-fixture-20260928-v1` 的测试分类 1 和文章 1–3。
实际修改字段只有 `eb_article_content.nid=1` 的 content，以及 `eb_article_category.id=1` 的 is_del。
测试文章始终保持隐藏、停用；未发布到正常展示。测试模式会读取隐藏文章，因此本轮使用分类软删除来验证撤回。
正常模式的单条隐藏过滤由同步命令自动测试覆盖，不由本轮测试模式代替。

修改前备份分类、文章及正文完整记录；每次修改/恢复都在事务中锁定记录并核对前态指纹，发现变化即拒绝覆盖。
恢复后完整记录 SHA-256 与基线相同（含状态与 visit）：

`a05508fffd823d56b694a44c0d71109a85ac95f2217edf93d7c22a3b51b7b73f`

临时网页服务正常退出（exit code 0），本机模型监听关闭。共 6 次本机 mock 请求，0 次外部模型请求，无 Embedding 调用。
没有删除测试文章或历史版本；本机临时证据保留用于排查。

## 证据与边界

原始结果：report.json（内部历史资料；已从公开历史移除，私密备份保留）。
同目录 `run.cjs` 和 `database.php` 保存本次实际使用的验收脚本，不包含数据库密码。
它们是固定本机路径、容器、ID 与标记的一次性验收记录，不是可直接用于其他环境的通用工具；不要直接在其他数据库重放。
临时构建目录为 `/tmp/omni-crmeb-chain-StRCAC`，容器输出目录为 `/tmp/omni-crmeb-chain-dkCLmK`。

此结果证明真实数据库变更能经适配器传到客服新检索，并在本轮注入的失败中保留旧版本。
不证明付费模型回答质量、历史回复撤回、处理中请求取消、语义检索、多实例同步或自动调度。
同一会话的历史仍可能含旧资料，空 snippets 不等于历史清除。
demo 身份仍为模拟身份，不代表已接通 CRMEB 用户身份、订单查询或业务写操作。

CRMEB 只作为数据源适配与验收样例，运行时知识重载不依赖电商业务字段。
建议下一阶段先接通真实宿主身份校验及用户隔离，再考虑只读业务查询。

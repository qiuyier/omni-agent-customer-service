# v1.1.0 知识管理：升级与回退说明

适用范围：从 v1.0.1/schema 2 升级到 v1.1.0/schema 3。公开状态以 GitHub v1.1.0 标签及 Release 为准，不要将分支 HEAD 当作正式发布产物。

## 新增能力与不变边界

独立管理员页面支持 FAQ 编辑、导入导出、发布前差异、单条试检索和批量报告、发布与回退；管理知识和操作记录持久化，旧 revision 请求被拒绝。客服使用已发布版本须显式选择 managed 来源。普通客户、坐席不会自动获得知识管理权限。

默认 start 仍固定回复；start-ai 仍使用 FAQ 文件；start-ai-managed 才使用数据库知识。没有自动导入 FAQ 文件、自动创建管理员或自动启用真实模型。仍是单业务独立实例、小规模关键词 FAQ，不是多租户共享知识、语义搜索或公网生产 IAM。管理历史上限和失败行为见 [存储说明](faq-management-persistence.md)。

## 升级步骤

1. 确认最终发布标签与附件校验和。记录当前应用版本、专用数据库版本、配置、管理员/业务身份来源与知识来源，禁止直接覆盖私密配置。
2. 安排维护窗口，停止客服写入和管理服务。对客服专用 PostgreSQL 做一致性备份，同时私密备份配置和旧应用产物；先在独立恢复副本验证备份可用。
3. 在该恢复副本用新版本 migrate 从 schema 2 升至 3，检查旧会话、消息、回执及人工接待状态保留，再验证新管理功能。通过后才按相同流程操作目标库。项目已完成 [虚构旧数据的 2→3 升级验收](schema-upgrade-acceptance-2026-11-08.md)，但不能代替你的目标库恢复副本验收。
4. 用新源码构建 migrate、webchat-server、knowledge-admin。确认 DATABASE_URL 指向客服专用库后，显式执行 migrate。程序启动不会自动迁移；新版本即使使用 fake 也要求 schema 3。
5. 保留原业务账号、宿主密钥和数据库密码，按 [参考部署](../deploy/reference/README.md) 运行 check 并启动原回复模式，先验证既有客服流程。
6. 如需管理知识，按 [知识管理指南](../deploy/reference/KNOWLEDGE.md) 创建独立管理员、导入、检查并发布；如需 AI 接待，再单独配置并选择 start-ai-managed。真实模型调用需确认资料授权和费用，不能用本地检查结果代替模型验收。

参考部署原有目录不重新 init；不删卷、不复制测试密码、不把账号文件或密钥写入发布包。生产接入仍需可信身份、HTTPS、专用库、备份恢复和运维责任人。

## 两种“回退”不能混淆

- **回退知识内容**：在新版本管理页选择历史发布版本并确认。不会降数据库版本，不改写历史聊天，不自动替换当前草稿。
- **关闭 AI / 改用文件模式**：停止 AI 客服进程，使用同一新版本的 start 或配置好的 start-ai；保留 schema 3 和管理知识，通常不需要整套应用降级。
- **退回 v1.0.1 应用**：旧应用严格要求 schema 2，不能直接连接已迁移的 schema 3。应先停止写入并保全升级后的数据库，再在隔离环境恢复升级前备份及匹配的旧程序/配置，验收后切换。恢复旧备份不会包含备份之后的新聊天和知识操作，必须明确处理这段数据后再执行；不是无损自动回退。

迁移 003 的 down SQL 会删除全部管理知识草稿、版本和审计。不得手改版本账本或直接 drop 表来绕过兼容检查；本项目没有提供或验收通用无损降级流程。

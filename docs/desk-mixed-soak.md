# 持续读写混合验收（2026-10-12）

本轮新增可复现测试和验收文档，未修改业务逻辑、CRMEB、前端、模型配置、索引或缓存。正式测试持续 601.0 秒（600 秒发起窗口，最后排空），结果通过。

## 负载与断言

- 两个来源，各 90 个预置待接入会话、每会话 100 条客户消息，共 18000 条预置消息；另有两个空种子会话。
- 4 条读写流程（每来源 2 条），每条约每 5 秒启动一轮；8 名独立坐席每秒刷新一次队列。共 12 个活跃身份，不等于 12 个请求始终同时执行。
- Go 测试进程内运行真实网关，使用真实回环 HTTP 和 PostgreSQL 16；应用池最多 4 条连接，网关沿用默认最大并发 16 和坐席限流。不是浏览器、Node/PHP 宿主或独立部署进程验收。
- 各流程创建新客户会话、申请人工、发送客户消息并重放原事件、查看历史、接管；随后并发执行“旧消息已读确认 / 新客户消息发送”，再发送人工回复并重放原事件。
- 新消息必须仍未读；确认新消息后必须为零未读。跨来源和同来源其他坐席读取已接管会话必须 403；最后核对恰好两条客户消息、一条人工回复的正文与角色，然后关闭会话。
- 刷新始终与上述流程并行；逐条验证来源和等待状态，预置会话的未读数及预览必须正确。闭环控制流仅让依赖前一步结果的动作顺序执行；不同流程及只读刷新并发。
- 不调用模型。模拟生成器已安装，但人工路径的实际生成器调用数为 0。

## 延迟与连接池趋势

下表是**各分钟 p95 的范围**及第一/第十分钟对比，不是全程 p95；不把分位数平均成全程分位数。HTTP 耗时包含请求编码到响应正文读取，不含后续 JSON 校验和直接数据库对账。

| 操作 | 第1分钟 p95 | 第10分钟 p95 | 各分钟 p95 范围 | 全程最大单次 |
| --- | ---: | ---: | ---: | ---: |
| 队列刷新 | 17.561 ms | 18.057 ms | 17.256–18.300 ms | 108.563 ms |
| 接管 | 7.811 ms | 9.281 ms | 7.811–10.792 ms | 14.280 ms |
| 客户发送 | 10.477 ms | 11.512 ms | 10.477–13.210 ms | 15.791 ms |
| 人工回复 | 7.487 ms | 7.820 ms | 7.272–8.717 ms | 11.433 ms |
| 已读确认 | 8.811 ms | 8.872 ms | 8.193–10.481 ms | 12.829 ms |
| 历史读取 | 10.454 ms | 11.395 ms | 10.454–12.721 ms | 31.909 ms |

接管等操作有小幅变化，不能宣称耗时完全不变；本样本未出现持续排队增长或请求失败。其他操作逐分钟数据保留在原始输出，包括申请人工的一次 67.770 ms 请求。

应用池保持 4 条总连接；39 次获取遇到空池，所有获取的累计耗时为 125.053 ms（包含正常获取成本，不是纯等待时间）。第 1 / 10 分钟累计获取耗时为 30.607 / 2.633 ms；未出现持续增长。第 9 / 10 分钟采样时分别有 1 / 2 条连接正在使用，最终排空后为 0；不能把进行中的占用当成泄漏。此处为分钟边界快照，不是全程峰值采样，也不覆盖服务器所有连接。

## 验证、复现和范围限制

先用 10 秒检查夹具，再运行正式 10 分钟；正式测量不启用 race。其后带真实数据库运行核心包完整 race 回归，并以 10 秒执行混合测试，均通过。全量 Go 测试、go vet 与 diff 检查通过。清表型数据库测试未与正式验收并行。

初次预检因复用 JSON 解码结构导致省略的 first_unread_id 保留旧值而误判；已修正测试解码对象，业务代码没有改动。正式通过记录来自修正后的完整运行，不拼接多次短测冒充 10 分钟。

仅对可丢弃且名称以 _test 结尾的专用库设置 TEST_DATABASE_URL。测试会清空客服表，不能连接业务库或持久化验收库。本次仅使用 standalone_rounds_20261009_test。

```sh
DESK_SOAK_DURATION=10s go test ./internal/persistence/postgres -run TestDatabaseDeskMixedSoak -count=1 -v -timeout 2m
DESK_SOAK_DURATION=10m go test ./internal/persistence/postgres -run TestDatabaseDeskMixedSoak -count=1 -v -timeout 15m
DESK_SOAK_DURATION=10s go test -race ./internal/persistence/postgres ./internal/webchat ./internal/conversation -count=1 -timeout 3m
go test ./...
go vet ./...
git diff --check
```

这是有节奏闭环的稳定性样本，不是极限容量或生产 SLA 认证；服务变慢会降低发起频率。数据规模增长仅 1440 条消息，不能外推至百万历史消息。测试没有包含断网、数据库重启、多进程/多副本、真实宿主认证、浏览器操作、真实 AI、知识隔离或业务系统写操作。每轮新建短期会话，不验证持有同一凭证超过其 TTL 的续期；双坐席抢接竞争见[上一轮并发验收](desk-concurrency.md)，本轮流程由单坐席接管。

## 接下来如何使用这些结果

当前没有证据要求加入缓存或更改索引。目标业务应按[试运行清单](host-onboarding.md#5-人工客服试运行验收清单)填明身份接入、期望负载、恢复措施、告警及开放范围，再做受控试运行；不能将本轮本机通过自动视作所有系统接入完成。

阅读顺序：本文 → internal/persistence/postgres/desk_soak_test.go（混合场景、逐分钟计量、最终总账）→ desk_concurrency_test.go（复用 HTTP/数据库测试环境）→ 原始证据 → 试运行清单。

本轮按性能分析技能记录负载、分阶段延迟和连接池成本，避免只依据单次耗时推断稳定性；技能的附属 load_testing.md 在本机缺失，沿用主文档流程完成。

# FAQ 知识管理：第一阶段核心

日期：2026-10-30。状态：管理核心及离线测试已实现，尚未接入产品。不是可用管理后台，也不是 1.1.0 已完成。

## 已确认边界

单业务独立实例、关键词 FAQ。管理入口与普通坐席权限分离；接入方可复用已有管理员登录，无后台的接入方后续提供独立管理员登录。客户或 staff 身份本身没有知识管理权限。不绑定 CRMEB，不做共享多租户、PDF/网页导入或语义索引管理。

## 本轮实现

- `faq.ParseVersion`：导入字节与已有文件加载共用严格校验，保留 1 MiB 上限、字段/条目约束、重复 ID 检查、未知字段拒绝及原始字节 SHA-256；旧 `Load` 仍拒绝空数组，版本加载允许显式 `[]`。
- `manage.Service`：查看状态、保存通过校验的草稿、发布草稿、回退已发布版本。保存草稿不会修改生效版本；发布/回退不覆盖草稿。
- 三个独立权限：`knowledge.read`、`knowledge.edit`、`knowledge.publish`。所有管理调用经过注入的可信身份授权器；调用方不能通过传入 actor 字符串自行取得权限。编辑权限不含发布权限。
- 全局 revision 乐观锁：保存/发布/回退均提交调用方看到的版本；竞争提交只允许一个成功，过期请求返回 conflict，不能静默覆盖别人修改。
- 状态、已发布内容与成功操作记录在同一 CAS 事务中提交；失败不得改变旧状态。事件包含可信 actor ID、UTC 时间、动作、前后知识版本及 revision，不包含凭据或正文。
- 空知识发布和回退均要求单独确认；损坏 JSON、校验失败或未知版本不等同于清空。
- 内部检索端口每次固定一个已发布快照，不读取草稿。存储异常或生效内容哈希不匹配返回错误，不伪装成合法空知识。已开始的检索可以继续使用旧版。
- 原始 FAQ 字节使用 `[]byte` 保存；JSON 快照使用 base64，避免 RawMessage 序列化压缩空白后造成哈希变化。将来 HTTP 编辑 DTO 应另外设计，不能直接把内部 State 当页面 API。

## 明确未完成

目前 Repository 是原子存储契约，只有测试文件中的内存实现。没有生产持久化、数据库迁移、HTTP 路由、管理页面、管理员登录实现，也没有替换现有 `KNOWLEDGE_FAQ_PATH`/信号重载链路。当前在线客服仍按 1.0.1 原逻辑运行。

生产适配层必须同时持久化状态和事件，提供隔离的读快照与真正 CAS；失败或提交结果不确定必须能通过 revision/状态核对，不能盲目重放。文件保存后另行 HUP 或审计追加不满足此契约。接线时须处理现有文件来源与管理来源的互斥，不能同时有两个发布者。

Authorizer 当前约定按每次管理调用核验身份、权限和撤销；登录到期/跨标签切号/迟到响应隐藏、CSRF、会话 cookie、限流以及安全日志仍须由后续适配层实现和测试。这里不把接口定义说成生产认证已完成。

初始保守限制：最多 32 个独立已发布版本、1000 条成功操作记录；到限拒绝而非静默丢审计。正式接线前需实现可持续的事务存储和审计保留策略，不能把内存快照方案直接上线。未实现失败尝试安全审计、草稿自动合并或一键删除历史。

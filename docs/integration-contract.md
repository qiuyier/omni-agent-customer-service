# 通用客服接入契约 v1

状态：2026-09-11 起草，2026-09-14 核对的文档约定与现有行为基线；不是新增 HTTP API 或已完成的多租户方案。

本文面向接入本服务的后端开发者。目标是让不同业务系统复用同一客服核心，而不是让
核心认识某一行业的数据表、字段或流程。电商等材料仅是隔离的测试样例。

文中标记含义：

- **已实现**：当前代码可执行的服务行为。
- **接入方责任**：调用方/渠道适配器必须实现或通过部署安排保证；本仓库不自动代办。
- **待实现**：设计边界或未来扩展要求，不能当成当前能力。

## 1. 角色、信任和部署边界

接入方是可信的业务后端或渠道适配器，不是持有服务凭证的终端客户。
浏览器、移动端或外部 webhook 应先进入接入方后端：由它核验用户身份、渠道签名、
访问权限，再转换为本服务的中性消息协议。不要把服务 Bearer Token 发给终端客户。

当前业务认证只有一枚实例级 `API_AUTH_TOKEN`，没有按凭证解析的接入方主体，
也没有会话级客户授权。请求中的 customer_id 和 channel 是调用方提供的数据，
不是服务验证过的最终用户身份。X-Request-ID 用于追踪，不是身份或幂等键。

两种部署方式都可以保持业务通用性，本契约不替项目选择：

| 方式 | 当前边界 |
| --- | --- |
| 每个接入方独立实例 | 可复用相同代码；应分别配置凭证、知识和存储，不能仅启动两个进程却共用未隔离数据库 |
| 多系统共用实例 | 当前只适用于同一信任范围内，由可信接入层统一身份与命名空间；不能向互不信任的系统分发同一 Token 后宣称已隔离 |

命名空间避免 ID 碰撞，不构成权限控制。共享部署若需要隔离接入方，必须另行实现
可信身份及作用域，贯穿会话、消息、知识、模型配置与存储查询；不能靠客户自报的字段
或模型从聊天内容猜测所属系统。本版本未新增 integration_id、tenant_id、Principal
等 HTTP 字段，也没有多接入方独立凭证、权限管理或配额功能。

## 2. 谁负责什么

| 能力 | 客服核心：已实现 | 接入方责任或待实现 |
| --- | --- | --- |
| 接收消息 | 校验并幂等存储客户文本，返回消息 ID、会话状态与 next_action | 核验客户/渠道身份；稳定映射源系统 ID；可靠保存入站事件 |
| 生成回复 | 显式 Trigger 生成、短事务保存、普通 JSON / SSE、已有回复重放 | 调度回复请求，维护待办、重试和超时；不是接收成功后自动生成 |
| 交付客户 | 返回已保存回复及其内部消息 ID | 按目标渠道投递、去重、记录送达结果；本服务无出站推送或送达确认接口 |
| 知识 | 统一 KnowledgeRetriever 端口；现成实现为本地 FAQ 的关键词/语义检索 | 提供合法且授权的资料；其他知识源需要适配器及装配配置 |
| 业务操作 | 当前只解释资料并给出指引 | 实时查询、外部写操作及人工接管 API 尚未实现，不能靠 Prompt 获得能力 |

“已存储”“已生成”“已送达”是不同状态；成功响应或 Duplicate 字段不能替代接入方的
处理记录。普通回复/SSE 的幂等保护不等于模型调用或下游交付恰好一次。

## 3. 当前标识与字段约定

权威传输定义为 [Thrift IDL](../idl/customer_service.thrift)；
下表不新增字段，不要求客户端依赖内部 ID 的具体格式。

| 字段 | 产生方与当前约束 |
| --- | --- |
| conversation_id | 接入方映射，放在 URL；在同一仓库全局唯一，创建后固定归属 customer_id＋channel |
| customer_id | 接入方从已认证用户映射；重放同一消息时保持一致；不得把用户随意填写的值当授权依据 |
| channel | 接入方设置的来源标识；与 external_message_id 共同构成去重键，不是隔离凭证 |
| external_message_id | 接入方提供的稳定事件 ID；在同一 channel 内跨会话唯一；超时重投不能换一个新 ID |
| content | 原客户文本，不能空白；重试必须保留原内容，不能为绕过冲突而改写 |
| message_id | 本服务生成；接收接口返回的是客户消息 ID，回复接口返回的是机器人消息 ID |
| trigger_message_id | 回复路径使用接收接口返回的客户 message_id，不能直接填 external_message_id |
| X-Request-ID | 单次请求追踪 ID，可使用新的值重试；不是客户身份、事件键或送达去重键 |

字符串标识当前会裁去首尾空白，content 不会被自动改写。接入方应在首次提交前固定映射，
后续重放使用相同有效负载。不要依赖大小写折叠等未定义行为。

例如，两个源系统都有会话 `42` 或事件 `event-1`，可信接入层应为它们保留独立、
持久且无歧义的映射；可使用接入层生成的内部 ID 或可逆编码后的名字空间。
不要直接拼接未经约束的用户输入；也不要把名字空间命名约定宣称为服务端授权。
目前相同 channel 下把 external_message_id 用于不同有效负载会返回冲突；相同有效负载
则是合法重放。会话 ID 撞名也不能作为两个独立会话共存。

消息只接受文本。接收接口固定写 customer 角色，不允许通过请求伪装为 system、
tool、bot 或人工坐席。附件、多模态、任意业务对象、语言偏好等不是当前声明的字段。

## 4. 接收与回复是两个独立步骤

### 4.1 接收

~~~http
POST /v1/conversations/helpdesk-session-42/messages
Authorization: Bearer <接入方后端持有的服务凭证>
Content-Type: application/json

{
  "customer_id": "user-27",
  "channel": "helpdesk-web",
  "external_message_id": "event-305",
  "content": "帮助中心在哪里？"
}
~~~

URL 的 conversation_id 优先，不能靠 JSON、query 或 form 改写目标会话；
只使用 IDL 声明的字段，不把未知字段作为受支持的扩展机制。
示例中的标识和文本都是虚构的，不包含真实客户信息。

首次成功返回 HTTP 201；相同消息重放返回 HTTP 200、原客户 message_id 和 duplicate=true。
接收时不存在的会话会被创建为 bot_active。首次消息的 next_action 是路由提示：

- generate_bot_reply：可安排回复工作；
- wait_for_human / deliver_to_human：由接入方处理对应人工流程；
- none：不安排新的动作；**不表示已生成或已送达回复**。

重复接收总是 next_action=none，status 是返回当时的会话状态，不是首次接收时的快照。
领域层已有人工/关闭状态，但当前 HTTP 没有请求接管、分配坐席、人工发言或关闭接口。

### 4.2 显式生成或恢复回复

~~~http
POST /v1/conversations/helpdesk-session-42/messages/<接收返回的message_id>/reply
Authorization: Bearer <接入方后端持有的服务凭证>
~~~

无须正文。首次回复保存成功返回 HTTP 201；已有回复返回 HTTP 200、duplicate=true，
且机器人 message_id 和 content 与原结果一致。没有已有回复时，只有机器人当前拥有
回复权、Trigger 仍是最新客户消息，才允许新生成。历史和资料在服务内组装，客户端
不能通过这个接口注入 system Prompt、角色历史或额外权限。

已有回复检查早于“当前回复权/最新 Trigger”检查：会话关闭、转人工或出现新客户消息后，
仍可能重放已保存的旧回复。**这只是历史结果恢复，不恢复机器人回复权，也不自动授权
再次投递给客户。**接入方必须根据自己的待办和渠道交付策略决定是否仍需发送。

回复已完成后的重复请求跳过知识检索和模型调用；首次完成前的并发尝试可能各自调用
模型，只有一个已保存回复成为最终结果。因此接入方应避免同一 Trigger 并发重试，
不得把存储幂等解释为供应商请求或费用恰好一次。

### 4.3 SSE

把上述回复路径追加 `/stream`。流建立后通常是 HTTP 200 / text/event-stream；
仅看 HTTP 200 不能判断是否生成成功，也不能照普通回复的 201/200 区分首次与重复。

- reply.delta：临时预览，未必会保存。可以替换/丢弃，不作为已完成消息。
- reply.completed：权威机器人 message_id、完整 content、duplicate；仅表示本服务已保存。
  最终文本以此事件为准，不能假设等于所有 delta 的拼接（并发时可能返回已保存的赢家）。
- reply.superseded：这次临时生成已失效，丢弃预览，不继续重试该次过期生成。
- error：流内安全错误事件；若此前未得到 completed，则未取得可确认的最终结果。

建流前的错误使用普通 Problem JSON；建流后不能仅依靠 HTTP 状态码处理错误。
重复请求也可能直接得到一个 completed，没有任何 delta；客户端必须支持这种情况。
该接口使用 POST，不提供浏览器原生 EventSource 的自动恢复协议，也没有已声明的
Last-Event-ID 增量续传契约。恢复使用相同 conversation_id＋trigger_message_id。

## 5. 失败恢复与交付责任

下面是**接入方应实现的流程**，不是服务内已有任务队列：

~~~text
可靠记录原始入站事件
  → 接收消息（不确定结果时按同一事件键重投）
  → 保存客户 message_id 和待办
  → 显式请求回复（不确定结果时恢复同一 Trigger）
  → 保存权威机器人 message_id / content
  → 向目标渠道投递并记录结果
~~~

记录的持久化、执行调度和渠道送达确认由接入方负责；本服务没有自动恢复待办、
出站 outbox、回调通知、回复列表或独立的只读回复查询 API。
调用 reply 恢复结果是“若不存在且条件满足则生成”，不是只读 GET。

### 接收已保存，但响应丢失

1. 接入方从自己的未完成事件记录恢复，以相同会话、客户、channel、external_message_id
   和原 content 重投。
2. 返回 duplicate=true、next_action=none 时，仍保存返回的原客户 message_id。
   它不证明已经回复；若接入方仍有未完成的自动回复工作，可显式恢复同一 Trigger。
3. 没有已有回复且不再满足机器人回复权/最新客户消息条件时，按冲突或前置条件错误处理。
   不要因为重复接收就无条件创建另一项回复工作，也不要用新事件 ID 绕开保护。

### 生成已保存，但响应或 completed 丢失

对同一 conversation_id＋trigger_message_id 重试普通回复或 SSE。已有结果会被重放；
如果结果尚未保存且仍符合条件，可能再次生成。不要把“我没收到最终事件”断言为
“服务没有保存”，也不要将旧 delta 与下一轮的 delta 接续成一条最终回复。

### 渠道投递响应丢失

机器人 message_id 是服务侧稳定交付标识。接入方可以用
“目标系统/渠道/接收方＋机器人 message_id”管理投递去重；若渠道支持幂等键，应复用
同一个键。若渠道不支持幂等或查询送达结果，就无法仅凭本服务承诺端到端恰好一次。
恢复投递不需要重新生成内容，也不应制造新的客户消息。

所有“跨进程重启仍可恢复”的服务侧保证均以持久存储为前提。
默认 MemoryRepository 在进程退出后丢失数据；需要该保证时配置 PostgreSQL，
并独立落实接入方待办记录的持久化。本轮没有运行真实 PostgreSQL 故障恢复实验。

### 公开错误与重试判断

服务返回 Problem 的稳定 code；不要解析人类 detail 来区分内部错误。
目前多个不同原因共用 conflict，接入方不能从一个 409 就可靠区分“ID 冲突”和“Trigger 过期”。

| 状态 / code | 接入方处理 |
| --- | --- |
| 400 invalid_argument | 修正字段、路径或 Trigger 关联，不能原样无限重试 |
| 401 unauthenticated | 修复凭证/接入配置；不换客户 ID 绕过 |
| 404 not_found | 核对映射、目标实例及存储状态；不能直接制造新的会话或事件掩盖问题 |
| 409 conflict | 查本地有效负载、ID 映射与最新消息工作记录；停止盲重试，不任意换键 |
| 412 failed_precondition | 当前会话/回复权不允许新操作；遵循状态流转，不反复触发生成 |
| 429 resource_exhausted | 有界退避重试；存在 Retry-After 时遵守它，不保证所有 429 都有该头 |
| 503 unavailable、504 deadline_exceeded、408 cancelled、连接中断 | 先视为结果可能不确定；在仍有处理意图且预算允许时按同一键恢复，持续失败转人工运维处理 |
| 500 internal | 保留追踪信息并告警；确认恢复条件后按原键处理，不能无限重试或泄露错误正文 |

503 可能是检索/模型错误，也可能是尚未配置回复能力，不能假设等待就一定恢复。
重试预算、退避、终止条件和人工兜底由接入方确定。日志避免客户正文、凭证与
供应商原始错误；安全保留必要关联信息，并按接入方隐私和保留策略管理处理记录。

## 6. 知识与外部业务能力

### 知识：接口已有，外部源需适配

[KnowledgeRetriever](../internal/customerservice/knowledge.go) 接收 Text/Limit，
返回 ID、Title、Source、Content。它不要求行业字段，也不要求特定模型或向量库。
实现须并发安全、遵守取消/超时，并区分“成功无匹配”与“后端失败”。

现成 server 通过启动配置加载单份 FAQ，支持 keyword/semantic，文件修改需重启；
当前不是远程文档上传 API、插件市场或跨系统知识同步服务。接入企业搜索、数据库或
其他知识服务可以实现现有接口并修改装配，不必重写客服用例；接口位于 Go internal
包，不是外部项目直接 import 的公开 SDK 或可动态注册的插件协议。

当前 KnowledgeQuery 没有用户权限或接入方作用域。不要把有不同访问权限的资料混入
同一实例的共享知识集后依赖 Prompt 隔离；需要细粒度访问控制时，先设计可信作用域
传递和资料过滤机制。知识内容一律是证据，不是授权或 system 指令。

### 业务工具：未实现

当前模型适配器只生成/提取文字。没有通用工具注册、执行循环、权限校验、执行确认、
调用 ID、结果关联或业务动作幂等协议。SenderTool 枚举和 AgenticModel 名称不代表
这些能力已存在；当前历史中的 tool 文本还被映射为 system 上下文，不能直接用于
不可信外部工具结果，接工具前必须改正该信任边界。

以下只是未来扩展要求，不是当前 HTTP 请求字段或即将自动实现的功能：

- 接入方在可信配置中声明允许的能力、输入/输出结构、授权身份、资源范围与超时；
  不向模型暴露凭证，不让聊天文本自行授予权限。
- 区分只读查询和有副作用操作；读取也须鉴权和最小化数据，写操作须明确授权、
  适当确认、幂等与审计，失败不能被解释为成功。
- 将工具结果作为不可信业务数据，并用调用 ID 关联，不能提升成 system 指令。
- 通用安全/证据规则与接入方业务规则、实际可用能力分离；只有已装配且已授权的能力
  才能进入能力声明。更换 Prompt 不等于安装工具。

当前没有工具的限制必须继续生效，不能为“显得通用”而删除不虚构操作结果的保护。

## 7. 接入验收清单

表中“服务回归”可以在本仓库离线验证；“接入方验收”仍需实际系统证明。
后续已新增[单活本地接入原型](integration-adapter.md)，覆盖稳定 ID、未完成记录和
模拟确认丢失恢复，不代表完成真实跨系统端到端验收。

| 项目 | 验收要求 / 归属 |
| --- | --- |
| 中性消息协议 | 仅会话、客户、来源、事件、文本；示例不依赖行业业务字段。服务回归 |
| 接收响应丢失 | 原键重投取得原客户 message_id，none 不误判为已回复，显式恢复生成。服务回归 |
| 回复响应丢失 | 重放同一权威消息，完成后不重复检索/调用模型；普通与 SSE 可交叉恢复。服务回归 |
| ID 错配与状态变化 | 冲突/前置条件失败不能盲重试；过期临时回复不保存；历史重放不恢复机器人权限。服务回归 |
| 未完成处理记录 | 进程崩溃后仍能恢复原始事件、Trigger 和投递状态。接入方验收 |
| 渠道送达 | 按权威机器人 ID 去重；正确区分保存、生成和送达。接入方验收 |
| 独立系统同名 ID | 按所选部署/映射方案不碰撞；多方共享时还须证明不能越权访问。接入方验收；服务多方授权待实现 |
| 知识与能力 | 仅使用获准资料，不因更换行业而改核心；外部知识适配器/工具按实际需求单独验收 |

新增 [恢复流程测试](../internal/transport/hertz/integration_recovery_test.go) 使用真实路由、
应用服务与内存仓库，模型/知识为 fake，SSE 使用内存写出器；通过不向模拟客户端保留
首次响应来覆盖恢复分支，并验证普通与 SSE 双向恢复、completed-only 重放。
这不是网络断连、进程崩溃、数据库灾备或真实渠道投递实验。

~~~bash
go test ./internal/transport/hertz -run TestIntegrationRecoveryAfterLostAcknowledgements -count=1
go test ./internal/conversation ./internal/customerservice ./internal/transport/hertz ./internal/bootstrap ./internal/ai/eino -count=1
~~~

当前 IDL、普通/流式幂等、过期 Trigger、关闭后重放等行为还由对应现有测试覆盖。
质量验收与接入契约验收分开：模型在某组模拟题答对，不证明接口可可靠接入生产系统。

## 8. 只读交付资格接口

`POST /v1/conversations/:conversation_id/messages/:trigger_message_id/reply/eligibility`

沿用现有 Bearer 鉴权、就绪检查、限流和请求日志中间件。JSON 请求体必填
`customer_id`、`channel`、`reply_message_id`、`content`；会话和触发 ID 以路径为准。
正常返回 200 与 `{"eligible":true,"reason":"eligible"}`，或 `eligible=false`。
拒绝原因包括 `ownership_mismatch`、`conversation_closed`、`not_bot_owned`、
`invalid_trigger`、`superseded`、`reply_mismatch`。缺少输入 400、缺少凭证 401、
会话不存在 404；其他错误沿用现有错误映射。响应禁止缓存。

一次会话事务读取归属、状态、消息和已存回复，不生成内容、不变更业务数据。
该接口不证明调用方拥有该客户的渠道发送权限，也不创建交付凭据或租约。
检查后的状态变化仍可能早于实际发送；严格条件发送必须由交付系统另行协调。
适配器每次重试重新查询，不复用允许结果，详见[交付前资格校验](integration-adapter.md#交付前资格校验)。

## 9. 下一步实施边界

鉴权、Prompt 或部署配置，不新增查询拆分或任何行业操作。

中性接入原型已实现稳定 ID 映射和“接收—回复—交付”处理记录，并以模拟响应丢失
用例验证，使用方式与限制见[接入适配器](integration-adapter.md)。是否托管处理队列、共享多方隔离、远程知识源和
外部业务工具，分别立项，不能混成“接入任何系统”一次性承诺。独立部署还是共享后台
仍需结合实际接入方需求选择，不是通用性本身的判断标准。

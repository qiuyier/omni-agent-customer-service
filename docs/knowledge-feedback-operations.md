# 未命中问题收集：部署与运行检查

本功能默认关闭，仅用于单业务 managed FAQ。规则脱敏不保证匿名化；上线前由部署方确认资料授权、用户告知和保留策略。不要将空列表当成采集成功的证据。本指南不授权修改任何已有部署。

## 升级与开启

1. 备份专用客服数据库和私密配置，先在独立恢复副本演练；不要连接原业务库。
2. 停止网关及知识管理进程，构建当前源码的 migrate、webchat-server、knowledge-admin。按原部署流程显式执行迁移。当前要求 schema 4；不能直接将旧二进制配新库运行，回退使用经过验证的完整备份恢复。
3. 首先保持采集关闭，启动知识管理并确认已有发布版本。参考部署见 [KNOWLEDGE](../deploy/reference/KNOWLEDGE.md)。
4. 在 `.local/reference/ai-managed.json` 原有五个模型字段之外添加布尔字段 `"captureUnmatched": true`；不改变原模型配置、不把密钥贴进日志，文件权限仍为 0600。省略或 false 表示关闭；普通 ai.json 不接受此字段。直接启动网关时对应 `WEBCHAT_KNOWLEDGE_FEEDBACK=true`。
5. 执行 `node deploy/reference/run.mjs check-ai-managed`。新增输出包括 `Feedback configuration (not running-process state)`、enabled、active/500 和 expired；数据库不可读时预检失败，不显示为队列为空。预检不调用模型、不写消息、不执行清理，也不能证明旧网关已应用新配置。
6. 停止旧客服进程，再执行 `node deploy/reference/run.mjs start-ai-managed`。必须在新网关成功监听、readyz 成功的前提下看该进程日志。不要只凭一条启动期日志判断服务可用。管理员用 `start-knowledge` 独立启动。

上述参考启动仍配置真实供应商，真实提问可能产生费用；本指南不要求通过真实提问验证。可先运行文末的独立模拟验收。

## 关闭采集但继续服务

将 captureUnmatched 改为 false（或删除字段），重新预检，再停止并重启 managed 网关。只改文件不会热更新运行中的网关。确认新进程日志 `capture=disabled`；已发布 FAQ 检索和模型回复仍工作，已有反馈不会立即消失，过期清理继续执行。

如需停用 AI，停止 AI 网关后执行普通 `start`；不会自动删除知识、反馈或历史消息。只停止所有客服/管理进程会暂停物理清理，不等于关闭采集仍保持清理。

## 看哪些运行状态

网关和独立管理进程向各自标准输出写 JSON 行，`event=knowledge_feedback_status`。启动时、每分钟及正常停止时输出，最多约一分钟可见延迟。采集热路径只更新内存计数，不逐条打印日志。输出不含问题、客户、会话、FAQ ID、底层数据库错误、地址或凭证；运行状态不挂在客户接口或 readyz 上。

| 字段 | 含义与边界 |
| --- | --- |
| capture | enabled/disabled 只表示这一网关进程的采集配置；管理进程为 not_owned，不能推断网关状态。 |
| recorded | 本进程确认写入成功次数，包括相同脱敏问题合并计数，不是独立问题或客户数。 |
| failed | 本进程采集写入失败或结果未确认次数；超时可能已提交，不可把它当成确定丢失数，也不自动重试。 |
| full | 新问题因 500 条上限未被收录的次数；不混同存储故障或成功采集。已有问题仍可合并计数。 |
| skipped | 零命中但检索预算不足或脱敏后文本无效等主动跳过次数，不是全部未采集消息总数。 |
| queue、active、expired | 数据库只读聚合快照。active 包含待处理/忽略/解决的所有未过期条目；expired 是尚待物理删除的过期行。queue 为 ok/full/unavailable；不可读时数量为 null，绝不以 0 代替。 |
| cleanup、cleanup_at | 本进程最近一次周期清理尝试的结果和时间：not_run/ok/failed。首次输出可能早于启动清理结束，应看后续输出。时间不是最近一次成功时间；没有删除行也可以是 ok。 |
| capacity、at | 容量固定为 500；at 是报告生成时间，不是服务启动时间。 |

计数和清理状态均为进程内存，重启归零，不跨网关与管理进程汇总；队列数来自共享专用库。当前不提供历史指标存储、自动通知或集中告警，部署方可采集进程输出另配告警。必须将日志正常接入运维系统，程序不能保证日志收集器可写或完整保存。

## 排错顺序

- **队列为空**：先确认对应网关确实启动 managed 且 capture=enabled；预检只说明配置。命中知识、重复事件、试检索/批量检查都不会产生新条目；预算不足会跳过，过期会不可见。
- **failed 增长 / queue=unavailable**：检查专用库连接、schema 4、权限和负载。不要把原始数据库报错、DSN 或问题正文贴入公开工单。采集失败不应中断正常检索；服务 readyz 成功不表示采集健康。
- **full 增长 / active=500**：容量保护生效。忽略/解决不会立即腾出容量，需等待首次采集后 7 天到期；不要未经备份手工删除表或扩大收集范围。
- **cleanup=failed**：检查数据库健康和进程日志输出。清理在启动和每小时执行，失败后等待下一次或在修复数据库后受控重启。持续运行且数据库正常时通常到期后 1 小时内物理删除；进程停机、故障、备份/WAL 副本不受此保证约束。
- **清理显示 ok 但仍有 expired**：计数与清理是不同瞬间的快照，新到期条目可等待下一周期。持续超过一个清理周期再排查；不要只靠一个瞬间的计数判定故障。

## 隔离验收（2026-11-10）

`node scripts/knowledge_feedback_flow_check.mjs --allow-test-writes` 使用随机新建容器/数据卷、真实网关和管理员进程、本机模拟模型。运行状态扩展后 14 项通过，5 次本机模拟模型请求，0 次外部模型请求；测试资源均清理成功。新增检查覆盖关闭时清理、开启后的采集计数与队列、管理进程 not_owned、重启归零和日志字段白名单。详见 [完整流程说明](knowledge-feedback-flow-acceptance.md)。

错误分类、容量满快照、队列不可读返回 null、底层错误文本不进入日志及并发计数由 Go 单元/竞态测试覆盖；本次未在运行中人为破坏数据库来触发采集故障，也未等待一小时清理周期。参考部署配置用例离线通过；未启动或改写用户现有 `.local/reference` 部署。无新迁移、无公开接口或管理页面变更。

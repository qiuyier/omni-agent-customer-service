# 分容器凭据轮换验收

## 范围和结论

本轮仅轮换业务宿主密钥与客户端 TLS 证书/服务端信任指纹；CA、服务端证书、坐席密钥和数据库密码不在范围内。复用通用干净业务，不修改 CRMEB、不调用模型。

这是有维护窗口的替换方案，不是无中断轮换。网关和 TLS 通道重建，业务登录进程保持运行；SIGUSR2 只重载该测试 worker 的客服适配层与本地 TLS 客户端，业务身份、Cookie 和原生登录不重启。没有在公共 HTTP 接口提供重载入口。

## 复跑

自动验收（报告路径必须不存在）：

```sh
node --test deploy/private-containers/*.test.mjs
node deploy/private-containers/check.mjs --allow-isolated-test-writes --report /tmp/rotation-new.json --rotation
```

浏览器模式使用交互终端，在上述命令后加 --browser。进入脚本输出的本机登录地址，用临时测试账号登录。只发送 BROWSER- 前缀虚构消息。

1. 发送轮换前标记。
2. 终端 rotate-stage：生成新证书/密钥，重建网关及通道，只接受新客户端指纹；此时旧客户端尚未更新，服务会拒绝访问。
3. 可选 rotate-bad-config：注入无效宿主密钥配置并触发重载，确认拒绝加载，不恢复旧信任。
4. 页面发送一条消息，确认显示待确认而不是成功。
5. rotate-activate：安装新客户端证书/密钥及新宿主密钥，发送 SIGUSR2，等待本次重载成功事件。不会仅凭文件替换就宣称生效。
6. rotate-verify：新证书+新宿主密钥应为 201；新证书+旧宿主密钥为 401；旧证书+新宿主密钥为 403。
7. 页面只点击一次“重试待确认消息”：同一业务身份允许更新聊天令牌并重试原消息。用 records 只读核对消息，再 stop 清理。详见 [恢复修复验收](chat-token-recovery.md)。

## 失败恢复规则

- 生成新材料或配置校验失败时，不自动切回旧凭据；修正新配置后显式再次激活。
- 无效配置在关闭旧适配层前被拒绝。如果旧凭据已经在网关被撤销，旧适配层仍不能访问网关。
- 新适配层启动失败时，入口保持 503，不能把未初始化状态当作成功。重载串行执行，测试覆盖拒绝、失败关闭及显式恢复。
- 撤销后不自动恢复旧证书指纹或旧密钥。只有确认旧凭据未泄露并重新获得部署授权，才可另行设计回退；本脚本没有回退旧凭据命令。
- 检测新旧组合均通过、业务会话正常、历史/回执一致后，才结束维护。失败则停止验收，不发布开放结论。
- 测试为证明旧凭据失效，暂时保留 retired-client 与 retired.json；它们只挂载到专用测试容器，结束时随临时目录删除。不能把这当作生产密钥保留策略。

## 2026-10-22 实测

自动轮换、错误配置恢复、旧凭据拒绝、业务登录保持、历史恢复、相同事件重试去重与回执一致全部通过；相关回归 77 项通过。[脱敏报告](evidence/private-rotation-2026-10-22.json)。

浏览器连续验收最终完成：轮换期间消息保留为待确认，恢复同一业务身份后第二次重试成功。数据库中轮换前、待确认两条标记各一份、同一会话。未重新输入业务账号密码。

已发现但未在本轮修改的体验问题：第一次重试使用旧聊天令牌，页面把 401 短暂显示成“登录已失效或身份发生变化”。业务登录实际仍有效，定时核对后恢复原身份和原待确认消息，需要再次手动重试。这不能称为无感恢复；后续应区分业务登录失效和聊天能力令牌过期，保留安全边界及原消息编号。

第一次浏览器验收未完成后测试环境结束，另一次环境启动失败，均未计为通过；最终重新完整执行。测试数据库就绪检查已改为 TCP，避免将初始化临时 Unix socket 服务当作可跨容器连接；没有足够证据把此前所有启动失败归因于此。

专用容器、网络、镜像、临时凭据和虚构数据已清理。没有推进发布，没有验证 CA/服务端证书轮换、跨机器或零停机。

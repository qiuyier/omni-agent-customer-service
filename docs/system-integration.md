# 新业务系统如何接入客服

统一执行入口：[通用客服接入交付指南](integration-delivery.md)，包含从空配置复跑、目标装配、验收和回退；本文作为接口职责参考。

可执行的阅读入口：[新系统最小接入包](../integrations/host-kit/starter/README.md)，包含配置样板、职责与逐项交接表。

现提供[仓库内可复用宿主接入包](../integrations/host-kit/README.md)：身份回调模板、受限代理和配置化本地验收器。它是参考后端包，不是任意登录协议或生产部署的免配置 SDK。

适用于电商、维修、内部服务等已有系统，**不要求业务系统已有客服模块**。CRMEB 只是一个实际身份适配例子，不是通用核心的前置依赖。

## 推荐部署方式

正式网关支持单宿主，或 WEBCHAT_HOSTS_JSON 多宿主（仅 fake/人工）。需要 AI/授权知识的业务仍按独立实例与数据库规划；每个业务必须使用独立稳定来源 ID 和随机宿主密钥，不能把来源标识当作知识隔离。

同一个核心程序可供不同系统复用；“系统可接入”不等于无需鉴权开发或不经目标环境验收。跨容器/跨主机网络需另行设计受保护通道，不能将仅供回环的私有接口直接暴露到公网。

## 业务系统提供什么

| 责任 | 最小要求 | 谁负责 |
| --- | --- | --- |
| 客户身份 | 已验证登录会话 → 稳定客户 ID；退出/切号可失效 | 业务系统适配器 |
| 员工身份 | 已验证客服员工及启用状态 → 明确授权坐席；不能由前端任选角色 | 业务系统适配器 |
| 会话和人工处理 | 保存消息、转人工、接管、回复、已读、关闭、新咨询 | 通用客服 |
| 同域页面与代理 | 复用聊天/Desk 页面；精确接口白名单、Origin/凭证绑定 | 业务系统适配器 |
| 可回答资料 | 该系统明确授权的 FAQ/知识；不提供时也可验证固定回复链路 | 接入方 |
| 业务操作 | 如查询维修单或退款，需要另行设计工具与权限 | 不属于最小接入 |

没有员工登录能力时，需先接企业身份系统或建设员工认证，不能把演示的“选择坐席”直接上线。没有运营资料不妨碍先用虚构资料和模拟回复验证接入。

账号禁用再恢复时，不应自动恢复旧登录的客服权限。宿主需在权威状态变更处原子更新权限版本或撤销旧会话；客服请求验证可信版本，包含禁用期间从未请求的旧登录。仅检查当前 status 不足以发现中间发生过禁用。CRMEB 的[权限版本实现](../integrations/crmeb/Identity-revocation.md)是一个适配示例，不要求其他宿主依赖其表、触发器或 JWT。

## 接口清单

这些是通用 Node 示例的公共路径，业务方可以自定义路径（CRMEB 使用 /api/omni-chat/*），但必须保持身份与请求语义一致，并为页面提供相应请求适配。

| 公共侧 | 适配器行为 / 私有网关 |
| --- | --- |
| GET /host/me | 当前已认证客户与可信 storage/reply_mode/human_enabled 元数据 |
| POST /host/chat-session，{} | 后端从登录取 ID，用宿主凭据调用 POST /internal/chat/sessions；绑定短期聊天凭证到该登录 |
| GET/POST /chat/v1/messages | 双重验证业务登录及聊天凭证；发送只接收 event_id/content |
| POST /chat/v1/message-receipt | 同样双重鉴权；只读核对原 event_id/content，返回 conversation_id/event_id/accepted，确认时附原 message_id；未知为 false，内容冲突 409 |
| POST /chat/v1/handoff，{} | 只作用于当前客户当前会话，不允许指定别人的 conversation_id |
| POST /chat/v1/consultations，{} | 仅关闭后创建新轮次；确认成功后失效旧绑定，再明确换取新会话 |
| GET /desk/me | 服务端已验证的坐席身份；不返回坐席密钥 |
| GET /desk/queue | 用该坐席独立凭据代理 /internal/chat/desk/queue |
| POST /desk/action | 用该坐席独立凭据代理固定 action 接口；history/claim/reply/read/close |
| 原业务登录/退出 | 保留业务原入口；适配器不能以调用错误角色鉴权为由误清另一角色登录 |

宿主凭据、坐席凭据、客户短期凭据是三种权限，不能混用。Cookie 本身不按端口隔离；部署时安排域名、Cookie 名/路径、HTTPS/Secure/HttpOnly/SameSite、CSRF 和服务端会话策略。
退出后要拦截迟到响应，但已经提交的消息不一定能撤回。发送结果不明时先查询原消息回执；未知或查询失败保留待确认，不自动重发。明确手动重试时沿用原 event_id/content，不能生成新事件。accepted 只证明收件，不证明已回复；未知不证明在途发送永远不会落库。关闭后可查询，但换轮次后旧凭据失效。

当前自动闭环基线为 `webchat-receipt-v1`，包括回执鉴权、隔离、冲突及只读验证。旧版通过报告不代表符合该基线；未开放回执的目标需补齐后重验，不跳过后标记通过。详见[统一验收](../integrations/host-kit/acceptance.md)。

## 接入顺序与完成标准

1. 从 [配置与启动清单](host-onboarding.md) 准备测试实例，先 fake；运行配置/资源预检，不请求模型。
2. 参考 [Node 独立宿主](../integrations/standalone-host/README.md) 或 [CRMEB 适配器](../integrations/crmeb/Human-acceptance.md)，接入真实客户/员工登录。
3. 验证两客户、两坐席的权限边界与人工闭环；不同系统即使原始 ID 相同也不能串数据。
4. 验证失败重试、退出/切号、新咨询和历史保留；涉及持久化应另外执行重启验收。
5. 最后才配置业务知识和真实模型；真实模型调用须获授权，固定回复测试不证明回答质量。

已有 [跨系统协议隔离回归](../integrations/cross-system/README.md) 使用两套真实 HTTP 模拟宿主与共享内存网关，核心代码未修改；它补充来源隔离证据，不替代真实目标系统或生产验收。

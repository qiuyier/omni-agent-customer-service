# 通用客服阶段盘点（2026-10-20）

基于仓库版本 `87841c6` 的代码、现有说明和历史验收记录进行静态盘点。本轮未运行新业务验收、未调用模型、未操作数据库、未修改业务逻辑或部署；下面的“通过”均指所链接记录的限定范围，不是本轮重测或生产批准。

## 一句话结论

当前是**具备真实接入与人工服务闭环的通用客服底座/仓库内参考接入包**，不是电商专用客服，也不是任意系统免开发即插即用的生产产品。没有现成客服模块的业务可以接；但必须有可信身份，完成适配、部署和该目标系统验收。

## 新系统实际需要提供什么

1. **认证契约**：服务端验证客户与员工登录的方法；稳定 ID、角色、启用状态、登录 sessionID、到期时间以及退出/禁用规则。共享浏览器边界还需公开登录版本；它不是凭据。
2. **人工授权映射**：哪些员工可做客服、映射到哪个坐席。能登录不等于有客服权限。
3. **页面和代理入口**：客户页/工作台路径、同源受限代理、Cookie 范围或 JWT 头适配、身份失效通知。
4. **运行责任**：客服专用 PostgreSQL、网关/适配器进程、来源 ID、独立服务密钥、迁移/备份/回退负责人。
5. **若启用 AI**：获授权的知识、模型与调用预算、可回答范围及质量验收；没有资料可先做 fake 技术验收，但不能冒充真实业务服务。

不需要把完整业务数据库开放给客服，也不需要业务原本已有客服模块。未来实时业务查询仅按明确工具契约最小授权，不等于读取所有业务表。

## 是否要修改原系统代码

- 通用 Go 客服核心通常无需随业务改动。
- 业务侧仍需实现认证映射、受保护代理、入口与页面装配。若原系统已有合适扩展点，可做附加模块；不能保证一行源代码都不改。
- Node 可复用 host-kit；PHP/Java 等按同一契约实现等价适配，或另设计可信边界服务。CRMEB 用附加 PHP 文件实现，不是把电商逻辑写入核心。
- 当前统一 CLI 验收偏向本机 Cookie/JSON 登录。JWT、SSO/MFA 或严格版本头需专门客户端，不能为验收方便降低原认证。
- 回环网关跨容器/跨机器部署需规划网络；“直接公网暴露私有接口”不是接入方案。

## 部署选择必须分开说

**现在可用的技术路径：**
- 单业务独立实例：fake/人工；可显式启用 AI 与该实例的知识，但仍需 AI 验收。
- 多业务同实例：当前仅 fake/人工。代码 `cmd/webchat-server/config.go` 明确在多宿主 + AI 时拒绝启动。

这不是“系统只能服务一个行业”。同一份程序可以给多个业务分别部署。共享多租户 AI/知识授权是另一项未完成能力，不应自动列为必须立即建设；只有明确需要共享 AI 实例时才优先做。

## 下一项建议：冻结“通用网页接入交付基线”

不是重写一套接入框架，也不增加新行业。依据是三个直接观察：

1. `host-kit/adapter.mjs` 和 `proxy.mjs` 已允许 `/chat/v1/message-receipt`，但 `verify.mjs` 当前路径集和闭环没有回执项。旧验收通过不能证明目标支持现在的恢复行为。
2. `docs/system-integration.md` 的公共接口清单遗漏回执；`integration-delivery.md` 排错仍主要引导查历史/同事件重试，没有明确“先查原事件回执”。
3. README 首先链接的 `integration-contract.md` 是 9 月旧服务 API 基线，含“人工接管 API 尚未实现”等旧描述；与现行 webchat 入口能力有明显时间/接口范围差异。必须标清旧 `/v1` 服务 API 与当前网页接入协议，不能无差别把历史 API 语义覆盖掉。

**建议下一轮完成标准：**

- 给当前网页接入一个明确的能力清单/版本范围，并把旧契约标注为对应入口的历史基线，保留旧证据。
- 在现有统一验收器增加可配置回执路径，核对已收、未知、冲突、跨客户、关闭后查询及退出拒绝；证明查询没有新增消息。
- 对不支持新能力的旧目标明确报“不满足本基线/待补”，不以旧闭环成功冒充完整通过；兼容策略必须明示。
- 更新 starter 交接表与阅读入口，同步“已收消息不等于已回复”、不自动重发和接口支持边界。
- 在已有非 CRMEB 参考链路回归，不再新造业务；CRMEB JWT 继续用专项验收，不强塞进 Cookie CLI。
- 不涉及生产部署、模型调用、订单工具或修改业务认证。

这一小步完成后，再按实际试运行目标选 AI 质量或部署恢复专项；不预设要做共享多租户平台。

# 恢复副本真实登录与 HTTP/浏览器验收（2026-10-21）

## 结果

在上轮恢复的独立 MySQL/PostgreSQL 副本上启动了原 CRMEB PHP 7.4 登录及客服适配代码、独立 Redis 和独立客服网关。两个客户账号与客服账号均通过原密码登录接口。轮换前客服接口可用，暂停测试入口、轮换 5 条身份版本后，三份旧登录均返回 HTTP 401；重新密码登录可用。

完整 HTTP 验收 10 项通过：客户会话分离、跨登录混用客服凭据拒绝、新客服登录可用、回执对应已接受消息、重复事件只存一次、另一客户不可见测试消息、客服接管、回复可见、关闭、关闭后重复读取历史不变。见同目录两份脱敏报告，不把这些计数与之前的数据库恢复检查合并。

浏览器使用临时测试表单调用真实 CRMEB 密码登录接口，客户和客服均显示登录成功；加载的是原安装的客户聊天和客服工作台构建文件。客户页显示固定回复模式、客户消息、演示回复和人工回复；刷新后仍为同一会话、三条消息各一条、状态为“本次咨询已结束”。客服工作台识别坐席，已关闭会话不在待处理队列。人工接管/回复/关闭由真实 HTTP 验收脚本操作，不声称全部通过鼠标完成。

## 隔离与边界

- 复用 `omni-restore-75fa50e693` internal 网络及该网络中的两份恢复数据库；未重启共享 PHP74，未更改原数据库、原 Redis 或原网关。
- 原 CRMEB 源码只读挂载；初始化之前覆盖数据库、缓存、签名密钥，客服配置单独只读挂载。运行目录在临时 PHP 容器内。
- 使用新生成的测试签名/网关密钥和空的独立 Redis，不复制原登录缓存。旧凭据指本轮副本真实密码登录后、轮换前取得的凭据，并非原环境的登录凭据。
- Docker internal 网络未能发布可用宿主机端口，因此使用只监听 `127.0.0.1` 的临时 Node 代理，通过 `docker exec` 请求隔离容器的真实 HTTP 服务。未为副本开放外网。
- PHP 内置 HTTP 服务运行原 ThinkPHP 路由/控制器，不是原 Nginx/FPM 部署；只允许登录、退出、客服 API 和测试资产路径。测试登录表单不是原商城登录页面。结论不覆盖生产 TLS、反向代理、容量、RTO/RPO。
- 全程 fake 回复，外部模型请求为 0，无业务订单操作；仅副本内有登录活动、权限轮换和虚构聊天写入。

## 探索失败与修正

首次人工流程验收脚本把服务端状态 `human_active` 误写为 `human`，导致断言失败，接管 API 本身已成功。修正的是临时验收脚本，不是产品代码。保留首次失败报告；关闭首次测试咨询，再完整重跑通过。

浏览器曾保留首次咨询的旧绑定；点击“开始新咨询”后对齐到 HTTP 验收已完成的新一轮咨询，并未跳过当前轮次。随后刷新确认历史和关闭状态不变。

## 证据与收尾

阅读顺序：本文 → `http-revocation-report.json` → `http-flow-report.json` → `http-flow-first-attempt.json` → `browser-report.json`。

私有备份、连接信息和登录凭据仍仅位于权限受限的临时目录，不加入仓库。验收结束后停止本轮代理、PHP、网关、Redis 和两份副本数据库；保留副本数据及备份供复核，不删除业务数据。原服务保持运行。

本轮补齐本地恢复后的真实登录、HTTP 和页面刷新验收，不代表已获得生产开放批准。下一阶段应形成可重复执行、失败默认保持停流的恢复验收入口，并明确正式部署中的备份保留、恢复时限和开放负责人。

## 结论

完整备份已恢复到独立 MySQL/PostgreSQL 容器：158 张业务表校验和一致；聊天消息、会话状态及坐席归属、已读记录、序列值和约束一致。

**恢复旧权限版本确实可能复活旧权限。** 在副本中使用实际 JwtAuth 和 IdentityRevision 签发/校验测试凭据，撤销后拒绝；再将版本恢复为备份时值，旧凭据重新匹配。恢复后统一轮换权限版本，旧客户/客服凭据均被拒绝，新签发凭据可用。

因此恢复不能以“数据库能启动”为完成标准。必须保持入口关闭，核对撤销触发器，轮换全部权限版本（包括已删除账号的记录），完成新旧凭据验收后再由负责人开放。

## 备份与隔离范围

MySQL 使用只读单事务逻辑备份，包含业务表、触发器、存储程序与事件；恢复库名使用独立随机名称，备份不含切回原数据库的 USE/CREATE DATABASE。恢复副本禁用事件调度器。PostgreSQL 使用 custom 格式备份，以 no-owner/no-privileges 恢复；数据与约束经过比对，不表示原角色授权已恢复，正式环境需要单独重建和验收最小权限。

两库分别取得快照，不是跨库同一事务或时间点恢复演练。生产备份需安排一致性窗口/停写和共同恢复点，不得由此次静态比对推出任意时点跨库一致。

副本只连接独立 internal Docker 网络，不发布端口。PHP 校验容器只读挂载原 CRMEB 源码，在框架初始化前改用副本数据库、临时文件缓存和独立测试签名密钥，不连接原缓存或使用原签名密钥签发测试凭据。

首轮数据库恢复成功，PHP 初始化仍读取原 Redis 配置而失败；已改为初始化前覆盖隔离配置，完整复跑通过。CLI 初次挂载点配置失败后已纠正。失败未改原库，不将探索过程伪装为一次全绿。

## 恢复工具

[IdentityRestoreGuard.php](IdentityRestoreGuard.php) 检查目标库、三张相关表的事务引擎、账号版本覆盖，以及 6 个触发器的事件/表/时机/逻辑。检查失败不轮换；通过后在事务内统一更新版本，失败回滚。它不做数据库导入、不自动重建缺失触发器、不开放流量。

[identity_restore.php](identity_restore.php) 默认只读。连接配置只能从 stdin 提供，数据库名还需在参数中显式确认；不读取原 CRMEB 默认配置，不在错误中输出连接信息。

配置格式（私有文件，权限 0600，不提交仓库）：

```json
{"host":"RESTORED_MYSQL_HOST","port":3306,"database":"RESTORED_DATABASE","username":"RESTORE_OPERATOR","password":"PRIVATE_VALUE","prefix":"eb_"}
```

```sh
# 检查；不会轮换版本。
php integrations/crmeb/identity_restore.php --database=RESTORED_DATABASE < /private/restore-target.json
# 仅在已切断客户/坐席入口、登录签发和相关写入后执行。
php integrations/crmeb/identity_restore.php --database=RESTORED_DATABASE --apply --confirm-support-offline < /private/restore-target.json
```

`--confirm-support-offline` 是操作者承诺，不是工具已验证网络停流。成功返回 `support_may_open=false`，不能据退出码直接重新开放。重复轮换会再次撤销期间签发的凭据，因此必须保持停流并安排重新登录。

## 必须遵循的恢复顺序

1. 停止新客服入口、登录签发及账号/聊天写入，确认目标数据库和共同恢复点；保留原环境与可回退备份。
2. 在隔离目标恢复业务库、版本表/触发器、聊天库；不要把原缓存和旧短期聊天能力凭据自动带入可访问环境。
3. 校验数据、状态、坐席归属、序列、约束；独立检查运行账号权限、配置、来源 ID 与坐席映射。
4. 执行工具默认检查。缺失/变化的触发器或缺失版本记录必须先调查，不得跳过或删除版本表重试。
5. 显式统一轮换权限版本，保留轮换结果；原业务登录是否全局撤销由业务身份策略决定，但旧登录必须不能访问新客服。
6. 用旧客户/客服凭据验证拒绝，再走真实重新登录、历史查询、回执和人工处理验收。确认 gateway 重启或更换实例使旧私有聊天凭据不可绕过代理。
7. 由负责人确认剩余安全、监控和容量项后开放；失败继续停流，不回滚权限版本以恢复可用性。

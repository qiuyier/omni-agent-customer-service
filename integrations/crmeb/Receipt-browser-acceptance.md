# CRMEB 浏览器异常回执恢复验收

后续[首次接管诊断](Claim-diagnostic.md)：已补齐代理异常日志，两轮复验首次接管成功；原偶发现象仍未定位，未改正式接管逻辑。

2026-10-20（Asia/Shanghai）。本轮三项目标通过：手动刷新恢复、切号隔离/切回恢复、人工关闭后整页恢复。未修改生产客服逻辑；增加可复用的本机故障验收工具与证据。

## 环境与测试方法

使用 `receipt-browser-lab.mjs --allow-test-writes`，仅监听 127.0.0.1 随机端口，固定上游为解析到回环地址的本机 `demo.crmeb.com`，启动时要求 enabled + fake + human_enabled。浏览器读取的是已安装的 CRMEB 独立客户页、客服工作台及其原构建资源，不是重写的聊天页面。

测试代理有一个简易登录页，调用真实 CRMEB 客户/客服登录接口，再按原前端约定在独立本机测试源存放凭据。不是在原商城登录表单内操作，也不是伪造用户身份。正式商城源的登录存储、原客服入口不改动。

代理只转发明确白名单路由，校验本机 Host/Origin，转发时适配上游 Origin；因此本轮不替代原域名下的 Origin 防护验收。故障通过终端显式布置：原发送/查询成功后，仅将浏览器收到的响应替换为 503。正式接口没有故障开关。报告不保存密码、登录令牌、客服令牌或响应中的凭据。

## 浏览器操作与结果

1. 客户一显式开始新咨询。第一条消息成功落库、页面收到 503，显示待确认；点击“刷新记录”，出现“已确认原消息送达”，待确认消失，恢复输入框。不点击重试。
2. 第二条消息同样保留待确认。额外让第一次回执查询返回 503，页面明确提示缓存保留，不误清。另一个登录页切到客户二，原客户页失效并清除旧显示；重新连接仅看到客户二原有记录，没有本轮客户一的消息或待确认。切回客户一后，原会话与待确认事件恢复，并通过查询清理；客户二没有清掉客户一缓存。
3. 客户一申请人工，在等待人工时发送第三条并注入 503。客服工作台接管并关闭；客户页整页重载后核实原事件，清除待确认，仍为 closed。再次重载没有恢复待确认，也没有重新开启会话。

## 请求证据与计数

原始 [report.json](../../examples/archive/integration/crmeb/2026-10-19T16-16-08-180Z/report.json) 保留工具的 passed=null/review_status；本文件记录人工浏览器审核结论，不将原报告伪装成自动浏览器测试。

- 3 个不同事件最终成功，3 条客户消息 + 2 条固定模拟回复；第三条处于等待人工，没有生成机器人回复。
- 实际消息 POST 为 **4 次**：第二条先收到 401，前端续签后沿用同一事件编号重试成功。不能声称“只有 3 次 HTTP 发送”。收到注入的 503 之后，刷新、切号恢复和重载没有再次发送原消息。
- 回执 POST 为 4 次，其中第二条的首次查询被注入 503；其余 3 次分别确认三条消息。每个回执的事件编号和消息 ID 都与已接收消息一致。
- 最后两次历史为相同 closed 会话，5 个消息 ID 无重复。再次重载未追加回执查询。
- 使用固定模拟回复，真实模型调用 0。代理路由/故障选择单元测试 2/2，前端全量 76/76；报告计数及事件/消息 ID 一致性额外用断言核对通过。

## 单独记录的现象

第一次点击客服“接管此会话”曾显示“操作未确认”。刷新队列、重新选择后第二次接管成功，随后关闭成功。原报告只有后一次成功 claim 记录，不能据此判定前一次失败发生在哪一层，也不能声称已定位/修复。没有因此重复发送客户消息，未阻断本轮回执目标；此现象作为独立待排查项保留。

## 收尾与重跑边界

临时浏览器页关闭，独立测试源客户 localStorage 和客服 cookie 已清除；代理停止。4 次由工具创建的登录均发送原生退出且 HTTP 成功返回（报告统计是 HTTP 结果，不单独声称再次鉴权验证注销）。原商城服务、数据库和测试历史保留，原用户页面不退出。无删除业务数据、无线上部署。

重跑会产生新测试消息、可能开启新咨询，并通过工作台关闭指定测试会话；仅用于已授权的本机测试库。先确认 fake 模式，不得用于生产。报告目录用 UTC 时间命名，本验收日期按 Asia/Shanghai 记录。

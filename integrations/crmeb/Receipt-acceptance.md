2026-10-20 已补充[浏览器异常恢复验收](Receipt-browser-acceptance.md)：刷新、切号及关闭后重载均通过；单独记录一次接管未确认现象，尚未定位原因。

2026-10-19：本机 PHP74 + CRMEB 原登录 + 通用网关 + 独立 PostgreSQL。已安装、更新并验收；固定模拟回复，真实模型调用 0。不是线上部署，也不是电商专用核心功能。

## 实现

新增 `POST /api/omni-chat/message-receipt`，仅允许 `event_id`、`content`，转发通用网关 `/chat/v1/message-receipt`。沿用 Origin/Host、商城登录、客服短期凭证绑定，以及响应返回前再次鉴权。拒绝 GET、注入会话字段和跨登录混用凭证。

CRMEB 前端在连接/重新加载以及手动刷新时调用公共 `reconcilePending`。原事件被明确确认且身份、轮次、缓存仍一致才清理待确认。自动历史轮询不查询回执；未知或错误不自动重发。查询不生成回复、不重开会话。“已送达”不等于“已回复”。

本次定点更新本机 CRMEB 的三个附加文件：`extend/omni_chat/Bridge.php`、`app/api/controller/OmniChat.php`、`app/api/route/omni_chat.php`，以及独立测试入口构建资源。安装前这三个文件与仓库版本一致。未改原登录、原客服入口、商品、订单、MySQL 表或用户已有的其他改动。

## 验证

- PHP 7.4：40 项桥接检查通过，包括新增回执转发、外来/同用户不同登录凭据、字段限制、内容冲突和查询中退出。
- 前端全量 76/76；新增 4 项 CRMEB 回执用例覆盖续签只重试查询、旧 200/401/503 不清理新身份缓存。初次测试的事件样本不是 UUID，触发正确的缓存格式校验；修正测试样本后全部通过，未放宽生产校验。
- CRMEB 前端构建、脚本语法和 diff 空白检查通过。
- 真实 HTTP 验收 26 项通过，使用用户提供的两个本地客户账号和一个客服账号，凭据仅从 stdin 输入。
- 原消息服务器接收成功后，验收客户端替换响应为 503；实际生产 CRMEB API 模块看到失败并保留待确认。切到另一账号无法查询原事件，切回原账号可通过公共恢复函数清理；混合登录/客服凭证返回 401。
- 未知事件保留缓存；相同编号不同内容 409；客服接管并关闭后重新获取会话，回执仍确认原消息，历史只含一次该消息，会话仍 closed；退出登录后查询 401。
- 整个真实验收只有一次消息 POST，恢复不重发。报告中 status=200 是原 HTTP 成功值，随后在测试客户端注入 503。

[真实链路报告](receipt-acceptance-report.json)。测试脚本为 `receipt_check.mjs`，会写入虚构测试消息并接管/关闭测试会话；只用于本机可写测试环境。退出脚本自行创建的登录，不退出用户原浏览器登录。

真实浏览器打开更新后的独立 CRMEB 入口，沿用原商城登录；显示本轮测试消息和模拟回复各一条、会话已结束。手动刷新及整页重载后身份、会话和历史不变。

CRMEB 关闭状态重载（内部历史资料；已从公开历史移除，私密备份保留）

本轮没有在真实浏览器里注入网络故障，也没有在浏览器里重放切号；故障恢复和账号切换覆盖来自真实 HTTP + 生产 API 模块/公共恢复函数及自动测试，不能把截图说成浏览器故障恢复全流程证据。上一轮通用页面的故障浏览器证据见[通用回执验收](../../docs/message-receipt-acceptance.md)。
